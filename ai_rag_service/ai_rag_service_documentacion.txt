1. FUNCIONAMIENTO
================================================================================

1.1. ¿Qué es ai_rag_service?
─────────────────────────────

ai_rag_service es un microservicio independiente construido con FastAPI que actúa 
como el "cerebro" de Mole-AI. Su función principal es recibir consultas de los 
usuarios sobre agricultura, procesarlas con inteligencia artificial y devolver 
respuestas especializadas en agronomía mexicana.

El servicio opera en el puerto 8001 y se comunica con el backend principal de 
Django (puerto 8000) mediante HTTP REST. No tiene contacto directo con el 
navegador del usuario; Django actúa como intermediario.

1.2. Capacidades del Sistema
────────────────────────────

    a) CHAT CONVERSACIONAL CON IA
       - Recibe la pregunta del usuario junto con datos de sensores.
       - Construye un prompt contextualizado con personalidad de agrónomo experto.
       - Envía la consulta a un modelo de lenguaje (LLM) multimodal.
       - Devuelve la respuesta interpretada con analogías sensoriales.

    b) GENERACIÓN DE EMBEDDINGS
       - Convierte texto en vectores numéricos de 768 dimensiones.
       - Utiliza el modelo sentence-transformers/all-mpnet-base-v2.
       - Los vectores se usan para búsqueda semántica en la base de conocimiento.

    c) INGESTA DE CONOCIMIENTO (PDFs)
       - Acepta archivos PDF con información agrícola.
       - Los fragmenta en chunks de texto procesables.
       - Genera embeddings de cada chunk y los almacena en un vector store (FAISS).
       - Permite que el sistema RAG recupere información relevante para las respuestas.

    d) ALERTAS TÁCTICAS AGRÍCOLAS
       - Analiza datos de sensores en tiempo real (temperatura, humedad, pH, UV).
       - Genera alertas automáticas cuando los valores están fuera de rango.
       - Las alertas se inyectan como prioridad máxima en las respuestas del LLM.

    e) MONITOREO DE SALUD
       - Endpoint /api/v1/health que reporta el estado de los modelos cargados.
       - Reporta tiempo de disponibilidad, uso de memoria y versión del servicio.

    f) DATOS DE SENSORES EN VIVO (Simulados)
       - Endpoint /api/v1/sensors/live que genera datos de sensores simulados.
       - Diseñado para ser reemplazado por un gateway IoT real en producción.

2.1. Arquitectura Hexagonal (Clean Architecture)
─────────────────────────────────────────────────

El servicio sigue la Arquitectura Hexagonal, también conocida como Puertos y 
Adaptadores. Esta arquitectura divide el código en tres capas concéntricas:

    ┌─────────────────────────────────────────────────────────┐
    │                    DOMAIN (Centro)                       │
    │   Modelos puros, interfaces abstractas, lógica de       │
    │   negocio. SIN dependencias externas.                   │
    │                                                         │
    │   Archivos:                                             │
    │   - domain/models.py           (15+ entidades)          │
    │   - domain/ports/              (interfaces abstractas)  │
    │   - domain/interfaces.py       (contratos)              │
    │   - domain/services/           (lógica de negocio)      │
    │     ├── prompt_builder.py      (personalidad del IA)    │
    │     ├── mole_ai_agricultural_service.py (alertas)       │
    │     ├── citation_manager.py    (gestión de citas)       │
    │     └── validator_service.py   (validación de inputs)   │
    │   - domain/exceptions/         (excepciones propias)    │
    │   - domain/security/           (seguridad de dominio)   │
    └───────────────────┬─────────────────────────────────────┘
                        │
    ┌───────────────────┴─────────────────────────────────────┐
    │                APPLICATION (Orquestación)                │
    │   Casos de uso que coordinan la lógica de dominio        │
    │   con la infraestructura.                                │
    │                                                         │
    │   Archivos:                                             │
    │   - application/use_cases/                              │
    │     ├── __init__.py            (exports centralizados)  │
    │     ├── mole_ai_chat_use_case.py  (caso principal)      │
    │     └── ingest_knowledge_use_case.py (ingesta PDFs)     │
    └───────────────────┬─────────────────────────────────────┘
                        │
    ┌───────────────────┴─────────────────────────────────────┐
    │              INFRASTRUCTURE (Mundo Exterior)             │
    │   Adaptadores concretos que implementan los puertos      │
    │   del dominio. Aquí viven las dependencias reales.       │
    │                                                         │
    │   Archivos:                                             │
    │   - infrastructure/ai/                                  │
    │     ├── llm.py                 (adapter HuggingFace API)│
    │     ├── model_manager.py       (gestión de modelos)     │
    │     └── vector_store.py        (FAISS vector store)     │
    │   - infrastructure/api/                                 │
    │     ├── routes.py              (endpoints FastAPI)      │
    │     └── contracts.py           (DTOs request/response)  │
    │   - infrastructure/data/                                │
    │     ├── pdf_parser.py          (ingesta de PDFs)        │
    │     └── conabio_loader.py      (datos CONABIO)          │
    │   - infrastructure/database/   (conexión a DB)          │
    │   - infrastructure/external/   (servicios externos)     │
    │     └── conabio_adapter.py     (API CONABIO)            │
    │   - infrastructure/messaging/  (mensajería/eventos)     │
    └─────────────────────────────────────────────────────────┘

2.2. Modelos de Dominio (domain/models.py)
──────────────────────────────────────────

Se definieron 15 entidades como dataclasses puras de Python:

    ENUMS:
    - UserRole          (admin, user, agricultor, system)
    - ModelType          (sentence-transformer, phi35-vision)

    ENTIDADES PRINCIPALES:
    - User              (id, username, email, role)
    - SensorData        (temperature, humidity, uv_index, soil_humidity, ph_level)
    
    ENTIDADES RAG:
    - RAGChunk          (id, content, metadata, score, vector)

    VISIÓN Y DIAGNÓSTICO:
    - VisionOutput      (description, confidence, tags, detected_objects)
    - DiagnoseRequest   (image, plant_id, region, description)
    - DiagnoseResponse  (diagnosis, confidence, recommendations)
    - FinalDiagnosis    (diagnosis, recommendations, sources_consulted)

    CHAT:
    - ChatRequest       (query, context, model, max_tokens, temperature, sensor_data)
    - ChatResponse      (answer, model_used, tokens_generated, processing_time_ms)

    EMBEDDINGS:
    - EmbeddingRequest  (text, model)
    - EmbeddingResponse (vector, dimension, model_used)

    SALUD:
    - ModelStatus       (model, is_loaded, loading_time_ms, memory_usage_mb)
    - ServiceHealth     (is_healthy, models_status, uptime_seconds, version)

2.3. Sistema de Prompts (domain/services/prompt_builder.py)
───────────────────────────────────────────────────────────

El PromptBuilder centraliza la construcción de prompts con las siguientes 
características:

    - Personalidad: Agrónomo mexicano senior con 25 años de experiencia.
    - Estilo: Analogías sensoriales (tacto, vista, olfato) en vez de jerga.
    - Estructura de respuesta:
        * Diagnóstico Visual (qué buscar)
        * La Receta (paso a paso)
        * Prueba del Tacto (verificación física)
        * Dato Experto (ciencia detrás)
    - Interpretación de sensores: Traduce números crudos a sensaciones.
      Ejemplo: "35% humedad" → "Suelo seco — si tomas un puño de tierra 
      y no se compacta, riega ya."
    - Priorización: Alertas tácticas > Sensores > RAG > Contexto > Consulta.

2.4. Servicio Agrícola (domain/services/mole_ai_agricultural_service.py)
────────────────────────────────────────────────────────────────────────

Sistema experto que contiene:

    - Base de datos de flora mexicana (maíz, frijol, chile, nopal, tomate, 
      manzanilla, jitomate) con parámetros óptimos de cultivo.
    - Generación de alertas tácticas basadas en umbrales de sensores.
    - Recomendación de tratamientos orgánicos por condición.
    - Análisis de suelo (pH, NPK, materia orgánica, textura).

2.5. Adaptador LLM (infrastructure/ai/llm.py)
──────────────────────────────────────────────

Clase Phi35LLMAdapter que implementa el puerto LLMGenerationPort:

    - Modo API: Llamada directa via aiohttp al endpoint de HuggingFace:
      POST https://router.huggingface.co/v1/chat/completions
      Formato OpenAI-compatible (messages[], model, max_tokens, temperature).
      Modelo actual: Qwen/Qwen2.5-VL-7B-Instruct.

    - Modo Local (deshabilitado): Carga del modelo completo en GPU/CPU local 
      usando transformers + AutoProcessor. Soporta visión (imágenes base64).

    - Gestión de errores: Manejo de respuestas no-JSON, errores HTTP, 
      timeouts de 120 segundos, y logging detallado.

2.6. Endpoints REST (infrastructure/api/routes.py)
──────────────────────────────────────────────────

    POST /api/v1/mole-ai/chat     → Chat conversacional con IA
    POST /api/v1/embeddings       → Generación de embeddings vectoriales
    GET  /api/v1/health            → Estado de salud del servicio
    POST /api/v1/knowledge/ingest → Ingesta de PDFs al vector store
    GET  /api/v1/sensors/live     → Datos de sensores simulados

2.7. Ciclo de Vida (app/main.py)
────────────────────────────────

El servicio utiliza el patrón Lifespan de FastAPI:

    INICIO:
    1. Cargar variables de entorno (.env)
    2. Inicializar ModelManagerAdapter (gestión de modelos)
    3. Inicializar FAISSVectorStoreAdapter (vector store)
    4. Inicializar PDFIngestionAdapter (parser de PDFs)
    5. Inyectar dependencias en los casos de uso
    6. Registrar rutas en la aplicación FastAPI
    7. Logging de todas las rutas disponibles
    
    EJECUCIÓN:
    - El servicio atiende peticiones HTTP en el puerto 8001.
    - Uvicorn con --reload para hot-reloading en desarrollo.
    
    APAGADO:
    - Descarga todos los modelos de memoria.
    - Libera recursos GPU/CPU.

3. FLUJO DE DATOS DETALLADO
================================================================================

3.1. Flujo Completo de una Consulta de Chat
────────────────────────────────────────────

A continuación se describe el recorrido completo de un mensaje del usuario 
desde que escribe "¿Cómo cultivar maíz?" hasta que recibe la respuesta:

PASO 1: USUARIO → FRONTEND (Navegador)
    El usuario escribe su mensaje en el input del chat (templates/index.html).
    El JavaScript (static/js/apiService.js) lo envía por WebSocket:
    
    ws.send(JSON.stringify({
        question: "¿Cómo cultivar maíz?",
        plan_id: "manzanilla"
    }))

PASO 2: FRONTEND → DJANGO BACKEND (Puerto 8000)
    El WebSocket consumer (apps/core/consumers.py) recibe el mensaje.
    Django lo procesa y lo reenvía como HTTP POST al servicio de IA:
    
    POST http://127.0.0.1:8001/api/v1/mole-ai/chat
    Body: {
        "query": "¿Cómo cultivar maíz?",
        "context": [],
        "sensor_data": {
            "temperature": 28.5,
            "humidity": 65.2,
            "soil_humidity": 42.0,
            "ph_level": 6.5,
            "uv_index": 7.1
        },
        "max_tokens": 1024,
        "temperature": 0.7
    }

PASO 3: FASTAPI → CAPA API (infrastructure/api/routes.py)
    El endpoint generate_mole_ai_chat() recibe el DTO MoleAIChatRequestDTO.
    Convierte los DTOs de infraestructura a entidades de dominio:
    
    SensorData(temperature=28.5, humidity=65.2, ...)
    ChatRequest(query="¿Cómo cultivar maíz?", sensor_data=sensor_data, ...)

PASO 4: CAPA API → CASO DE USO (application/use_cases/mole_ai_chat_use_case.py)
    El MoleAIChatUseCase.execute() orquesta todo el proceso:
    
    a) VALIDACIÓN: InputSanitizer valida y limpia la consulta del usuario.
    b) ANÁLISIS DE SENSORES: MoleAIAgriculturalService analiza los datos 
       de sensores y genera alertas tácticas si algún valor está fuera de rango.
       Ejemplo: temperatura > 35°C genera una alerta CRITICAL de estrés térmico.
    c) DETECCIÓN DE CULTIVO: Identifica que la consulta menciona "maíz" y 
       recupera información de la base de flora mexicana.
    d) BÚSQUEDA RAG (si hay vector store): Busca documentos relacionados con 
       "cultivar maíz" en el vector store FAISS para enriquecer la respuesta.
    e) TRATAMIENTO ORGÁNICO: Si se detecta un problema, busca recetas de 
       tratamientos orgánicos en la base de conocimiento interna.
    f) CONSTRUCCIÓN DEL PROMPT: Delegado al PromptBuilder.

PASO 5: CASO DE USO → PROMPT BUILDER (domain/services/prompt_builder.py)
    PromptBuilder.build_chat_prompt() ensambla el prompt completo:
    
    ─── SYSTEM PROMPT ───
    Eres Mole-AI, un agrónomo mexicano senior con 25 años de experiencia...
    [Reglas de comunicación sensorial, analogías, estructura de respuesta]
    
    ─── ALERTAS TÁCTICAS ───
    (Si las hay) 🚨 [CRITICAL] Estrés térmico: temperatura 28.5°C...
    
    ─── DATOS DE SENSORES ───
    🌡️ Temperatura: 28.5°C → Cálido — rango ideal para cultivos tropicales.
    💧 Humedad ambiental: 65.2% → Buena humedad ambiental.
    🌍 Humedad del suelo: 42.0% → Humedad baja, necesita agua pronto.
    ⚗️ pH del suelo: 6.5 → Ligeramente ácido — ideal para maíz.
    ☀️ Índice UV: 7.1 → UV alto, revisar hojas.
    
    ─── BASE DE CONOCIMIENTOS (RAG) ───
    (Fragmentos relevantes de PDFs ingestados)
    
    ─── CULTIVO DETECTADO ───
    Maíz (Zea mays) — Cultivo básico mexicano...
    
    ─── CONSULTA DEL USUARIO ───
    ¿Cómo cultivar maíz?
    Recuerda: responde usando analogías sensoriales...

PASO 6: CASO DE USO → ADAPTADOR LLM (infrastructure/ai/llm.py)
    Phi35LLMAdapter._generate_response_api() envía el prompt al LLM:
    
    a) Construye el request HTTP:
       POST https://router.huggingface.co/v1/chat/completions
       Headers: Authorization: Bearer hf_xxxxx
       Body: {
           "model": "Qwen/Qwen2.5-VL-7B-Instruct",
           "messages": [{"role": "user", "content": "[PROMPT COMPLETO]"}],
           "max_tokens": 1024,
           "temperature": 0.7,
           "stream": false
       }
    
    b) Envía la petición con aiohttp (timeout: 120s).
    c) Recibe la respuesta en formato OpenAI-compatible:
       {
           "choices": [
               {"message": {"content": "Para cultivar maíz, primero..."}}
           ],
           "usage": {"completion_tokens": 450}
       }
    d) Extrae el texto de choices[0].message.content.

PASO 7: ADAPTADOR LLM → CASO DE USO (Respuesta)
    El caso de uso recibe el ChatResponse y lo enriquece:
    
    a) Inyecta alertas tácticas al inicio de la respuesta si existen.
    b) Agrega recetas de tratamiento orgánico si se detectó un problema.
    c) Formatea la respuesta final.

PASO 8: CASO DE USO → CAPA API → DJANGO → FRONTEND
    La respuesta viaja de regreso:
    
    MoleAIChatResponseDTO → HTTP 200 → Django consumer → WebSocket → 
    JavaScript (apiService.js) → Renderizado en el chat (main.js):
    
    {
        "answer": "Para cultivar maíz, primero siente la tierra...",
        "model_used": "Qwen/Qwen2.5-VL-7B-Instruct (API)",
        "tokens_generated": 450,
        "processing_time_ms": 8500,
        "tactical_alerts_count": 0
    }

3.2. Flujo de Ingesta de Conocimiento (PDF → Vector Store)
──────────────────────────────────────────────────────────

PASO 1: Administrador sube un PDF vía POST /api/v1/knowledge/ingest.
PASO 2: PDFIngestionAdapter extrae texto del PDF y lo fragmenta en chunks.
PASO 3: Cada chunk se convierte en un embedding de 768 dimensiones.
PASO 4: Los embeddings se indexan en el vector store FAISS.
PASO 5: Cuando un usuario pregunta algo, el sistema busca los chunks más 
        similares semánticamente y los inyecta como contexto RAG en el prompt.

3.3. Flujo de Sensores en Tiempo Real
──────────────────────────────────────

PASO 1: Frontend ejecuta GET /api/v1/sensors/live cada 5 segundos.
PASO 2: FastAPI devuelve datos simulados (o reales de un gateway IoT).
PASO 3: Frontend actualiza los indicadores del dashboard Pip-Boy.
PASO 4: Al enviar un mensaje de chat, los datos de sensores actuales se 
        adjuntan automáticamente al request como sensor_data.
PASO 5: El PromptBuilder interpreta los valores con analogías sensoriales.
PASO 6: El servicio agrícola genera alertas si los valores son críticos.

4. JUSTIFICACIÓN
================================================================================

4.1. ¿Por qué un microservicio separado?
─────────────────────────────────────────

    a) SEPARACIÓN DE RESPONSABILIDADES: El procesamiento de IA es 
       computacionalmente costoso y tiene requerimientos diferentes al backend 
       web. Separarlo permite escalar cada servicio independientemente.

    b) CICLO DE VIDA INDEPENDIENTE: Los modelos de IA necesitan cargarse en 
       memoria al inicio y liberarse al apagar. Este ciclo de vida es 
       incompatible con el modelo request-response de Django.

    c) TECNOLOGÍA APROPIADA: FastAPI es asíncrono por naturaleza, ideal para 
       llamadas HTTP a APIs externas (HuggingFace) que pueden tardar segundos. 
       Django es síncrono por defecto y requiere workarounds para IO-bound tasks.

    d) DEPLOYMENT FLEXIBLE: El servicio de IA puede desplegarse en una máquina 
       con GPU mientras el backend web se ejecuta en un servidor más económico.

4.2. ¿Por qué Arquitectura Hexagonal?
──────────────────────────────────────

    a) TESTABILIDAD: Los casos de uso y la lógica de dominio se prueban sin 
       necesidad de una conexión real a HuggingFace o a una base de datos.

    b) INTERCAMBIABILIDAD: Se puede cambiar de HuggingFace a OpenAI, Ollama 
       o cualquier otro proveedor de LLM modificando únicamente el adaptador 
       en la capa de infraestructura, sin tocar la lógica de negocio.

    c) MANTENIBILIDAD: Las reglas de negocio agrícola (umbrales de sensores, 
       base de flora mexicana, recetas orgánicas) viven en el dominio, 
       aisladas de cambios en la API o la infraestructura.

4.3. ¿Por qué RAG (Retrieval-Augmented Generation)?
────────────────────────────────────────────────────

    a) CONOCIMIENTO ESPECIALIZADO: Los LLMs generales no tienen conocimiento 
       específico sobre plagas del nopal en Oaxaca o tratamientos orgánicos 
       para chile serrano. RAG permite inyectar este conocimiento.

    b) ACTUALIZACIÓN SIN REENTRENAMIENTO: Se pueden agregar nuevos PDFs con 
       información agrícola actualizada sin necesidad de re-entrenar el modelo.

    c) CITABILIDAD: RAG permite rastrear de qué documento provino cada pieza 
       de información, lo que genera confianza en las recomendaciones.

    d) COSTO: Entrenar un modelo especializado costaría miles de dólares. 
       RAG logra resultados comparables usando un modelo general + contexto.

4.4. ¿Por qué el modelo Qwen2.5-VL-7B-Instruct?
─────────────────────────────────────────────────

    a) MULTIMODAL: Soporta tanto texto como imágenes, habilitando diagnóstico 
       visual de plantas en el futuro.
    b) DISPONIBLE EN TIER GRATUITO: Está soportado por los proveedores de 
       inferencia de HuggingFace sin costo adicional.
    c) CALIDAD COMPETITIVA: 7B de parámetros ofrece un buen balance entre 
       calidad de respuesta y velocidad de inferencia.
    d) FORMATO OPENAI-COMPATIBLE: La API de HuggingFace Router usa el mismo 
       formato que OpenAI, facilitando migración futura.

4.5. ¿Por qué comunicación sensorial en las respuestas?
───────────────────────────────────────────────────────

    a) ACCESIBILIDAD: Los agricultores en campo no siempre tienen instrumentos 
       de laboratorio. Instrucciones basadas en los sentidos (tacto, vista, 
       olfato) permiten verificar sin equipo especializado.
    b) RETENCIÓN: Las analogías cotidianas ("como una esponja exprimida") se 
       recuerdan mejor que porcentajes técnicos (60% de capacidad de campo).
    c) ACCIONABILIDAD: Una instrucción sensorial es directamente ejecutable, 
       mientras que un dato técnico requiere interpretación adicional.


================================================================================
5. CONCLUSIÓN
================================================================================

El ai_rag_service representa el componente más crítico y técnicamente sofisticado 
del sistema Mole-AI. Su diseño en capas hexagonales garantiza que:

    1. La lógica agrícola mexicana está protegida de cambios tecnológicos.
    2. El proveedor de IA puede cambiar sin afectar el negocio.
    3. El conocimiento se puede expandir continuamente vía PDFs.
    4. Las respuestas son científicamente correctas pero humanamente accesibles.

El flujo de datos demuestra cómo una simple pregunta del usuario desencadena una 
cadena de procesamiento que incluye: validación, análisis de sensores, generación 
de alertas tácticas, búsqueda semántica, construcción de prompts contextualizados, 
inferencia con un LLM multimodal, y enriquecimiento de la respuesta.

El servicio actualmente funciona con inferencia remota vía HuggingFace API, lo 
que permite ejecutarse sin GPU local. Para producción, se recomienda:

    - Activar RAG funcional con pgvector/FAISS e ingestar documentos agrícolas.
    - Implementar caché de respuestas para consultas frecuentes.
    - Conectar sensores IoT reales en lugar de datos simulados.
    - Habilitar streaming (SSE) para respuestas progresivas.
    - Agregar diagnóstico por imagen aprovechando la capacidad multimodal.

El resultado es un sistema que transforma datos técnicos en conocimiento 
accionable, democratizando el acceso a asesoría agronómica especializada para 
agricultores de cualquier escala en México.
