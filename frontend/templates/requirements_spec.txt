Requisitos Funcionales (RF)

RF-01: El sistema DEBE permitir a un usuario autenticarse mediante credenciales (usuario y contraseña) contra el endpoint `auth/login/`. Al autenticarse correctamente, el cliente DEBE recibir y almacenar un token JWT utilizable para peticiones autenticadas.

RF-02: El sistema DEBE permitir registrar nuevos usuarios mediante el endpoint `auth/register/` y mostrar un mensaje de confirmación en la UI. Tras el registro exitoso, la UI DEBE redirigir a la pantalla de inicio de sesión.

RF-03: El sistema DEBE presentar un motor de tipeo (typewriter) en el contenedor `#typewriter-output` que reproduzca progresivamente el texto para las secciones `objetivo`, `vision`, `flora` y `acerca`. Invocar el buscador o navegación a otro módulo DEBE detener inmediatamente la animación activa.

RF-04: El frontend DEBE centralizar el enrutamiento de eventos UI mediante atributos `data-action` y una tabla `ActionMap` (Event Router). Al hacer clic en cualquier elemento con `data-action`, el router DEBE invocar el handler correspondiente y pasar la referencia del elemento clicado como argumento.

RF-05: El componente "Buscador de Flora Mexicana" DEBE inyectarse en `#typewriter-output` cuando se active `type:flora` y DEBE incluir: un campo de texto `input#flora-search-input`, un contenedor `div#flora-search-results` y estado visual de carga. El campo DEBE recibir foco automático tras la inyección.

RF-06: El Buscador DEBE realizar búsquedas al endpoint `${window.AppConfig.API_BASE_URL}/plants/search/?q=<query>` con debounce de 300 ms y solo para queries de longitud >= 2 caracteres. Las respuestas DEBEN mostrarse en `#flora-search-results` como tarjetas clicables que permitan expandir una ficha técnica.

RF-07: El Buscador DEBE garantizar coherencia de resultados: las respuestas de búsquedas previas canceladas o abortadas NO DEBEN sobreescribir los resultados visibles (uso de cancelación/AbortController o equivalente).

RF-08: El sistema DEBE permitir descargar reportes PDF desde el historial mediante botones que expongan `data-action="report:download"` y `data-report-id`. El router DEBE invocar la función que descarga el PDF preservando el estado visual del botón (descargando/éxito/error).

RF-09: El wizard de vinculación IoT (ESP32) DEBE ejecutar pasos secuenciales y exponer controles de cierre/confirmación vía `data-action` manejados por el router; finalizar el wizard DEBE dejar visible el botón `#new-user-plants`.


Requisitos No Funcionales (RNF) y Restricciones

RNF-01 (Zero-dependencies): El cliente web DEBE funcionar sin frameworks externos; solo HTML5, CSS3 y JavaScript ES6 estándar. Cualquier biblioteca añadida DEBE justificarse y aprobarse por la dirección técnica.

RNF-02 (Seguridad de Autenticación): El cliente DEBE almacenar y enviar JWT en el header `Authorization: Bearer <token>` solo cuando exista un token válido; si no hay token, el header NO DEBE enviarse. La gestión de claves DEBE soportar claves legacy y canonical (ej. `moleia_token` → `mole_jwt`).

RNF-03 (Protección XSS): Cualquier dato externo (respuestas API, inputs de usuario) que se inserte en el DOM DEBE ser tratado como texto plano por defecto. Si se necesita renderizar HTML, este DEBE pasar por un sanitizador aprobado (p. ej. DOMPurify) con lista blanca de etiquetas/atributos.

RNF-04 (Latencia y UX): La interacción del Buscador DEBE mostrar un estado de carga en menos de 100 ms tras expirar el debounce; las respuestas cacheadas o locales DEBEN completarse idealmente en <500 ms para mantener UX fluida.

RNF-05 (Cancelación y GC): Operaciones asíncronas repetidas (p. ej. búsquedas) DEBEN soportar cancelación mediante `AbortController` y DEBEN liberar listeners/recursos al destruir la UI para evitar fugas de memoria durante sesiones largas.

RNF-06 (Observabilidad): Acciones críticas y errores DEBEN registrar logs con prefijos y contexto (p. ej. `[Router] loadFloraSearch invoked`, `[Flora] HTTP 504`) para facilitar debugging y pruebas automáticas.


Criterios de Aceptación (Buscador de Flora)

AC-01 (Inyección y foco): Al activar `type:flora` mediante el router, en la consola DEBE aparecer exactamente la línea: `[Router] loadFloraSearch invoked`; además, el DOM DEBE contener `input#flora-search-input` y `div#flora-search-results` en menos de 200 ms y `#flora-search-input` DEBE tener el foco.

AC-02 (Debounce y petición correcta): Al escribir una query de 3 caracteres en `#flora-search-input`, tras 300 ±50 ms se DEBE emitir exactamente una petición HTTP GET a la URL `${window.AppConfig.API_BASE_URL}/plants/search/?q=<urlencoded-query>`. Si se escribe una nueva query antes de recibir la respuesta, la respuesta antigua NO DEBE actualizar `#flora-search-results`.

AC-03 (Renderizado seguro y expansión): Dada una respuesta JSON con al menos un objeto que contenga `name`, `scientific_name` y `description`, el cliente DEBE:
- Renderizar una tarjeta por objeto dentro de `#flora-search-results` (uno a uno).
- Al clicar la tarjeta, mostrar la ficha expandida con los campos como texto plano (sin ejecución de HTML ni scripts) y un control para cerrar que restaura la vista de lista.
- Verificar con un payload malicioso (p. ej. `description: '<img src=x onerror=alert(1)>'`) que NO se ejecuta ningún script; el campo DEBE mostrarse escapado o como texto.
