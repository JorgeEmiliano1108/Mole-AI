IMPLEMENTATION REPORT — Self-Updating RAG (Knowledge Harvesting) — DETAILED
Date: 2026-03-14
Author: Dev Assistant

1) Resumen ejecutivo
--------------------
Esta entrega implementa la capacidad de "Self-Updating RAG" (harvesting de
conocimiento) en el servicio `ai_rag_service`. Cuando la búsqueda vectorial (FAISS)
no devuelve resultados con calidad suficiente, el sistema consulta APIs botánicas
externas (Trefle / FarmVillage) mediante `BotanicalFallbackGateway`, transforma
esa respuesta en contenido textual, deduplica con SHA-256, genera embeddings y
persiste el contenido en una tabla `botanical_knowledge` en Supabase y en el
vectorstore FAISS. Crucialmente, por directiva de seguridad, la persistencia se
realiza en **Supabase primero** y **FAISS sólo si Supabase tuvo éxito** — si
Supabase falla se evita por completo la escritura en FAISS para mantener
consistencia entre almacenamiento durable y el índice local.

2) Objetivos funcionales
-----------------------
- Proveer fallback de conocimiento cuando FAISS no aporte contexto útil.
- Harvesting idempotente: evitar duplicados mediante hash SHA-256.
- Persistencia dual (durable + rápida) con regla transaccional definida.
- Inyectar el nuevo conocimiento en el prompt del LLM para la misma petición.
- Añadir pruebas unitarias que cubren los caminos críticos (éxito, fallo en
  Supabase, deduplicación).

4) Contratos y supuestos (importantes)
--------------------------------------
- `VectorStorePort`:
  • `async def add_documents(self, documents: List[str], metadata: List[dict]) -> int`
  • `async def retrieve(self, query: str, top_k: int = 3) -> List[RAGChunk]`
  RAGChunk.score se espera en escala 0..1 (implementación FAISS la normaliza).

- `EmbeddingPort` (usada indirectamente por vector_store): se mantiene la

  principal (GenerateEmbeddingUseCase delega a `embedding_service.generate_embedding`).

- `BotanicalFallbackGateway.fetch_tolerance(species_name)` → Optional[dict]
  retorna un dict con `min`, `max`, `optimal`, `source`, `scientific_name`.

- `SupabaseBotanicalRepo` usa PostgREST: requerimientos en env: `SUPABASE_URL`,
  `SUPABASE_KEY` (service role) para inserts/upserts.

5) Lógica crítica: pseudocódigo del flujo de harvesting
------------------------------------------------------
- Si no hay `vector_store` o `knowledge_repo` configurados → return None.
- Llamar `ext_data = botanical_gateway.fetch_tolerance(query)`.
- Si `ext_data` es None → no hay nada que persistir.
- Construir `content` textual y `content_hash` SHA-256.
- Si `knowledge_repo.get_by_hash(content_hash)` devuelve fila → dedupe: skip.
- Intentar `knowledge_repo.save_botanical_entry(...)`:
  • Si falla → log error; return contenido en memoria (no persistido).
  • Si OK → intentar `vector_store.add_documents(... )`.
    - Si FAISS falla → log error para reconciliación (no revertimos Supabase).
- Devolver dict con keys: content, source, persisted/bools.

10) Riesgos y mitigaciones
--------------------------
- Licensing: contenido externo puede tener restricciones — guardar `source` y
  `provenance` (URL) junto al texto; añadir flags para excluir fuentes no
  permitidas.
- Rate limits: Trefle/FarmVillage tienen límites — proteger con backoff,
  caché por `content_hash` y circuit-breaker.
- Consistencia: decidimos Supabase como fuente de verdad. No implementamos
  transacciones distribuidas; mitigación: reconciliador y logs para auditoría.
