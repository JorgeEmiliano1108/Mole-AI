1) `mole_ai_backend/settings.py`
- Propósito: configuración central del proyecto Django/ASGI. Define `INSTALLED_APPS`, `DATABASES`, `REST_FRAMEWORK`, `CACHES`, `CHANNEL_LAYERS`, variables de terceros (Supabase, HF), logging, static/media y otros parámetros de entorno.
- Componentes clave:
  - `INSTALLED_APPS`: incluye `channels`, `rest_framework`, `pgvector`, `core`, `ai_models`, `authentication`, `plants`.
  - `AUTH_USER_MODEL = 'authentication.User'` — determina el modelo de usuario global.
  - `REST_FRAMEWORK`: autenticaciones por defecto (`SupabaseAuthentication`, `HardwareAPIKeyAuthentication`), permisos `IsAuthenticated`, parsers, throttles y rates.
  - `DATABASES`: usa SQLite cuando DEBUG=True; Postgres (Supabase) en producción.
  - `CHANNEL_LAYERS`: Redis en producción, InMemory para desarrollo.
  - `MOLE_AI_SERVICE_URL` y `MOLE_AI_API_KEY`: variables críticas para la comunicación con el microservicio FastAPI; fail-fast en producción si faltan.
- Observaciones:
  - Hay un mecanismo `path_config.py` opcional para ajustar `sys.path` y rutas de apps.
  - `HARDWARE_API_KEY` usado para endpoints M2M; se advierte si no está configurado.
  - Logging escribe en `logs/django.log` y consola.
- Recomendaciones:
  - Asegurar que `.env` documente todas las variables críticas (FASTAPI_URL, MOLE_AI_API_KEY, HARDWARE_API_KEY).
  - Revisar throttles y ajustar tasas en producción según carga real.

2) `manage.py`
- Propósito: entry point CLI para comandos Django (`migrate`, `runserver`, `createsuperuser`, etc.). Standard Django wrapper.
- Observaciones: sin cambios.

3) `entrypoint.sh`
- Propósito: script Docker entrypoint usado por `Dockerfile` y `docker-compose` para esperar DB, aplicar migraciones y arrancar Daphne.
- Flujo:
  1. Espera que la DB acepte conexiones (loop de socket).
 2. Ejecuta `python manage.py migrate --noinput`.
 3. Ejecuta `collectstatic` (silencioso) y arranca `daphne`.
- Observaciones:
  - Es robusto para contenedores (wait-and-retry). En entornos on-prem es apropiado.
  - No aplica fixtures ni crea `superuser` — operación manual recomendada.
- Recomendaciones:
  - Considerar crear un `createsuperuser --noinput` controlado por variables de entorno para despliegues iniciales automáticos (con precauciones de seguridad).

4) `Dockerfile` y `docker-compose.yml`
- `Dockerfile`: base python:3.11-slim, instala dependencias del sistema (build-essential, libpq-dev), instala paquetes Python de `requirements.txt`, copia el proyecto y pone `entrypoint.sh` como ENTRYPOINT.
- `docker-compose.yml`: define servicios `django_backend`, `fastapi_rag`, `db` (pgvector), `redis`, `mqtt_broker`. Montajes y variables de entorno listadas.
- Observaciones:
  - `fastapi_rag` tiene healthcheck y depende de `db` y `redis`.
  - `django_backend` expone puerto 8000 y usa `volumes: .:/app` para desarrollo.
- Recomendaciones:
  - En producción eliminar mounts que exponen código fuente.
  - Asegurar variables de entorno sensibles (no en control de versión). Usar secretos en orquestador.

5) `requirements.txt`
- Contiene dependencias clave: Django 4.2, channels, djangorestframework, psycopg2-binary, pgvector, django-redis, httpx, python-dotenv, reportlab, etc.
- Observaciones:
  - Las versiones son mayormente compatibles; verificar compatibilidad con Python 3.12 (entorno actual usa 3.12 en tests). Algunos paquetes (psycopg2-binary) deben compilar en ciertos entornos.

6) `apps/authentication/infrastructure/repositories/models.py` (modelo `User`)
- Propósito: implementación del `User` personalizado.
- Campos destacados: `supabase_uid`, `supabase_role`, `supabase_app_metadata`, `avatar_url`, `phone_number`, `is_premium`, `subscription_expires`, `created_at`, `updated_at`.
- Observaciones:
  - `db_table = 'auth_users'` — tabla con nombre explícito.
  - Propiedad `full_name` y método `has_subscription()` incluidos.
- Recomendaciones:
  - Mantener sincronización de campos con Supabase; documentar proceso de reconciliación de usuarios (cuando un usuario se crea en Supabase vs local DB).

7) `apps/plants/infrastructure/repositories/models.py`
- Propósito: modelos domain para catálogo de especies (`SpeciesCatalog`) y asociación usuario-planta (`UserPlant`).
- Campos relevantes:
  - `SpeciesCatalog` incluye ideal ranges (humidity, temp, ph).
  - `UserPlant` usa `UUID` PK para `id` (plant_id usado por ESP32) y FK `user` a `AUTH_USER_MODEL`.
- Observaciones y recomendaciones:
  - Mantener `plant_id` stable es crítico para dispositivos IoT; no cambiar PK type.
  - Si se añade `ph_level` en `SensorLog`, correlacionar con `ideal_ph_*` en `SpeciesCatalog` para alertas.

8) `apps/core/infrastructure/repositories/models.py`
- Propósito: modelos de dominio del core (SensorLog, BotanicalKnowledge, AIDiagnostic, DiagnosticoGeolocalizado, FeedbackTicket).
- Resumen de modelos:
  - `SensorLog`: wide-table para telemetría con `id BigAutoField`, `plant_id UUID`, `recorded_at`, columnas sensor (soil_humidity, air_temperature, uv_index, light_level). *Actualmente falta `ph_level` que está referenciado en Serializers y Views.*
  - `BotanicalKnowledge`: chunks de conocimiento con embedding `VectorField` (pgvector) — usado para RAG/consulta.
  - `AIDiagnostic`: registros de diagnósticos generados por AI (UUID PK), metadata e imagen.
  - `DiagnosticoGeolocalizado`: geolocalización de diagnósticos con FK a `AIDiagnostic`, `user` y `severity`.
  - `FeedbackTicket`: nuevo modelo agregado (ver resumen anterior).
- Observaciones:
  - `SensorLog` needs `ph_level` field to align with serializers/views (bug detectado).
  - `BotanicalKnowledge` almacena embebimientos — revisar tamaño y estrategia de retención si la DB escala.
- Recomendaciones:
  - Implementar migración para `ph_level` (FloatField) en `SensorLog`.
  - Revisar índices y particionado (si la tabla crece mucho, considerar retención o partición temporal).

9) `apps/core/models.py` (re-export)
- Propósito: re-exportar modelos definidos en `infrastructure/repositories/models.py` para que Django los detecte en `core.models` como convención de este repo.
- Observaciones: necesario para migraciones y admin discovery.

10) `apps/core/admin.py`
- Propósito: registro de modelos en Django Admin. Se agregó `FeedbackTicketAdmin` con `list_display`, `list_filter`, `search_fields` y `readonly_fields`.
- Observaciones: admin facilita gestión de tickets por admins no-técnicos.

11) `apps/core/presentation/serializers.py`
- Propósito: validación y transformación de entrada/salida para endpoints del core.
- Serializers relevantes:
  - `SensorReadingSerializer` y `SensorBatchSerializer` — validan telemetría wide-table (requieren al menos un sensor field). Incluyen `ph_level` en validación (por eso mismatch con modelo actual).
  - `DiagnosticRequestSerializer` — valida uploads de imágenes con límites (10MB) y tipos permitidos.
  - `HotspotSerializer` — formato de salida para frontend (nombres en español esperados por UI).
  - `FeedbackTicketCreateSerializer` y `FeedbackTicketResponseSerializer` — añadidos para el nuevo endpoint.
- Observaciones:
  - Mantener sincronía entre serializadores y modelos; actualmente `ph_level` rompe esa sincronía.

12) `apps/core/presentation/views.py`
- Propósito: implementar lógica de endpoints REST del core.
- Endpoints importantes:
  - `sensor_data_view` (POST) — ingestión M2M (auth por API key hardware). Valida y persiste en `SensorLog`.
  - `sensor_batch_view` (POST) — bulk ingest para edge nodes (max 500). Valida plant_ids provisionados y usa `bulk_create`.
  - `diagnostic_view` (POST) — carga imagen y crea `AIDiagnostic` invocando servicios de IA.
  - `map_hotspots_view` (GET) — reconstruye hotspots para frontend.
  - `feedback_create_view` (POST) — nuevo, crea `FeedbackTicket` con `request.user`.
- Observaciones:
  - Varios endpoints usan `HardwareAPIKeyAuthentication` o `IsAuthenticated` según sea M2M or user.
  - `sensor_batch_view` y `sensor_data_view` pasan `ph_level` a `SensorLog` → TypeError en tests.

13) `apps/core/presentation/urls.py`
- Propósito: rutas del core, incluidas `sensor-data/`, `diagnostics/`, `map/hotspots/`, `feedback/`.

14) `apps/core/migrations/0005_botanicalknowledge_feedbackticket_and_more.py`
- Propósito: migración monolítica que incluye creación de `FeedbackTicket` y ajustes en modelos previos.
- Observaciones: Django empaqueta cambios pendientes, por eso 0005 incluye varios cambios. Validar que los cambios remuevan/alteren campos intencionadamente.

15) `ai_rag_service/` FastAPI microservice (carpeta)
- Propósito: microservicio de IA (RAG/embeddings/LLM) consumido por Django. Sigue arquitectura hexagonal.
- Endpoints clave: `/v1/embeddings`, `/v1/chat/generate`, `/v1/health`.
